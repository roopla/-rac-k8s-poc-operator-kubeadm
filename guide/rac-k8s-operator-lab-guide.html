How to use this guide

This guide builds a second lab, the operator lab, next to the manual lab you already have. It follows the manual guide's Phases 0 and 3–6 step by step, with its own names, addresses and ports, so the two labs never overwrite each other. The RAC database itself will come from Oracle's database operator in the later phases, instead of the hand-run installs of the manual lab's Phases 8–14.

Copy every block exactly as it is. Each block's label says where it runs, and the connect line shows how to get there. Blocks labelled # PowerShell run in a PowerShell window on your PC, never in Git Bash.

This lab's output blocks after a Check show what this lab's own run printed, so you can compare your screen line by line. Long logs are cut to the lines that matter (… marks a cut); where a step first went wrong, that output is shown too, labelled, next to the corrected run. IDs, UUIDs, image IDs and times will differ on your build. Steps without such a block weren't captured during this run (most of Phases 4 and 5).

Phase 0Windows host and the operator lab's port forwards

Result of this phase: a clean starting point for the operator lab, the PC checked for room, and SSH port forwards 2220–2222 on the shared k8s-public network. The manual lab and the golden VM are not touched.

0.0 Start clean (only if you built the operator lab before)

What: removes an earlier operator lab: the VMs op-controlplane, op-worker1, op-worker2, the folder D:\VMs\rac-op with all its disks, the operator lab's port-forward rules, and the SSH host keys remembered for ports 2220–2222. On a first build it just reports that there's nothing to remove.

What it never touches: ol98-golden, controlplane, worker1, worker2, D:\VMs\rac-poc and the k8s-public network itself. Every name in the block starts with op- or rac-op.

PowerShell
$VB = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"; $Base = "D:\VMs\rac-op"
$existing = (& $VB list vms) -join "`n"
foreach ($v in "op-worker1","op-worker2","op-controlplane") {
  if ($existing -match ('"' + $v + '"')) { & $VB controlvm $v poweroff 2>$null; Start-Sleep 3; & $VB unregistervm $v --delete; "removed VM $v" }
}
$left = (& $VB list hdds) | Select-String '^Location:\s+(.*)$' | ForEach-Object { $_.Matches[0].Groups[1].Value } | Where-Object { $_ -like "$Base\*" }
foreach ($d in $left) { & $VB closemedium disk $d --delete; "removed disk $d" }
if (Test-Path $Base) { Remove-Item $Base -Recurse -Force; "removed folder $Base" }
foreach ($r in "ssh-opcp","ssh-opw1","ssh-opw2","k8sapi-op") { & $VB natnetwork modify --netname k8s-public --port-forward-4 delete $r 2>$null }
foreach ($f in "$env:USERPROFILE\.ssh\known_hosts", "$env:USERPROFILE\.ssh\known_hosts_rac_lab") {
  if (Test-Path $f) { foreach ($p in 2220, 2221, 2222) { ssh-keygen -R "[127.0.0.1]:$p" -f $f 2>$null | Out-Null } }
}
"--- VMs (the manual lab and ol98-golden must still be listed; no op-*) ---"
& $VB list vms

Check: list vms still shows ol98-golden, controlplane, worker1 and worker2, and no op-* VM.

Phase 3Clone the three operator-lab nodes

Result of this phase: three VMs (op-controlplane, op-worker1, op-worker2) cloned from the same golden image as the manual lab, the workers with two data disks each and their private NICs on op-priv1 / op-priv2, and three new disks that both workers share for ASM: 10 GB for VOTEDG, 50 GB each for DATA and FRA.

3.1 Check that the golden VM is still sealed

Why: clones must come from the sealed golden image: no machine ID, no SSH host keys. You sealed it before cloning the manual lab. If the golden VM has been started since then, it has made itself a new machine ID and host keys, and every clone would share them. Kubernetes refuses to join nodes with the same machine ID.

How to tell without starting it: VirtualBox records when a VM last changed state. If the golden VM's last change (its power-off after sealing) is older than the manual lab's clones, nobody has started it since.

PowerShell
$VB = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"; $g = "ol98-golden"
$info = & $VB showvminfo $g --machinereadable
$state = ($info | Select-String '^VMState="(.*)"').Matches[0].Groups[1].Value
$raw = ($info | Select-String '^VMStateChangeTime="(.*)"').Matches[0].Groups[1].Value
$changed = [datetime]::SpecifyKind([datetime]::ParseExact($raw.Substring(0,19), 'yyyy-MM-ddTHH:mm:ss', $null), 'Utc')   # VirtualBox writes UTC
$cpCfg = (& $VB showvminfo controlplane --machinereadable | Select-String '^CfgFile="(.*)"').Matches[0].Groups[1].Value
$cloned = (Get-Item (Split-Path $cpCfg)).CreationTimeUtc   # when the manual lab's controlplane was cloned
"manual lab folder:    $(Split-Path $cpCfg)"
"golden state:         $state"
"golden last changed:  $($changed.ToString('u'))"
"manual lab cloned:    $($cloned.ToString('u'))"
if ($state -eq 'poweroff' -and $changed -lt $cloned) { "OK: still sealed, not started since the manual lab was cloned" } else { "STOP: golden VM was started after the seal; reseal it (below)" }
& $VB snapshot $g list

Check: the line says OK: still sealed…, and the snapshot list shows the pre-seal snapshot. Then go straight to 3.2. The block finds the manual lab's folder from VirtualBox itself, wherever it is on your disk.

3.2 Clone and size the nodes

Why these sizes: the same as the manual lab. op-controlplane gets 2 vCPU and 4 GB with no private NICs; each worker gets 4 vCPU and 22 GB, an 80 GB disk for /scratch and a 100 GB disk for /var/lib/containers.

What's different: the workers' second and third NICs move from the manual lab's internal networks rac-priv1 / rac-priv2 to the operator lab's op-priv1 / op-priv2. The clones inherit the golden VM's NIC settings, including the "Allow All" promiscuous mode Multus needs; only the network names change.

PowerShell
$VB = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"; $Base = "D:\VMs\rac-op"; $g = "ol98-golden"
while ("$(& $VB showvminfo $g --machinereadable | Select-String '^VMState=')" -notmatch 'poweroff') { Start-Sleep 3 }
foreach ($n in "op-controlplane","op-worker1","op-worker2") { & $VB clonevm $g --name $n --basefolder $Base --mode machine --register }
& $VB modifyvm op-controlplane --cpus 2 --memory 4096 --nic2 none --nic3 none
foreach ($w in "op-worker1","op-worker2") {
  & $VB modifyvm $w --cpus 4 --memory 22528 --intnet2 op-priv1 --intnet3 op-priv2
  & $VB createmedium disk --filename "$Base\$w\$w-scratch.vdi" --size 81920 --variant Standard
  & $VB createmedium disk --filename "$Base\$w\$w-containers.vdi" --size 102400 --variant Standard
  & $VB storageattach $w --storagectl SATA --port 1 --device 0 --type hdd --medium "$Base\$w\$w-scratch.vdi"
  & $VB storageattach $w --storagectl SATA --port 2 --device 0 --type hdd --medium "$Base\$w\$w-containers.vdi"
}
foreach ($n in "op-controlplane","op-worker1","op-worker2") { "--- $n"; & $VB showvminfo $n --machinereadable | Select-String '^(cpus|memory|nic[123]|nat-network1|intnet[23])='; & $VB showvminfo $n | Select-String '^NIC [23]:' }

Check:

  • op-controlplane: cpus=2, memory=4096, nic1="natnetwork" with nat-network1="k8s-public", and nic2="none", nic3="none";
  • each worker: cpus=4, memory=22528, nat-network1="k8s-public", intnet2="op-priv1", intnet3="op-priv2", and two NIC 2: / NIC 3: lines that include Promisc Policy: allow-all, each with its own MAC address. 3.3 The shared ASM disks

What: three disks attached to both workers at once, one per ASM disk group:

Disk Size SATA port Disk group Holds
vote1.vdi 10 GB 5 VOTEDG the cluster's own files: voting file, OCR, the ASM password file and spfile
asm1.vdi 50 GB 3 DATA the database's data files, control files and redo logs
asm2.vdi 50 GB 4 FRA the fast recovery area: archived logs, flashback logs, backups

Why three disk groups instead of one: keeping the cluster's files apart from the database makes each easier to size, move and repair; a full FRA can't stop the cluster, and the clusterware disk group stays small. The manual lab put everything into one DATA disk group.

Why port 5: the SATA controller has six ports (0–5). Port 5 carries the golden VM's empty DVD drive, which the clones inherited and nothing uses; the block removes it and puts vote1 there.

Why fixed size and shareable: RAC is a shared-disk database, so both nodes need the same block devices; VirtualBox only allows the shareable type on fixed-size disks, and without it refuses to attach the second VM. These are new, empty disks in D:\VMs\rac-op\shared; the manual lab's disks stay with the manual lab. Don't snapshot the workers: VirtualBox can't snapshot a VM with shareable disks. Creating the fixed disks takes a few minutes.

PowerShell
$VB = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"; $Base = "D:\VMs\rac-op"
New-Item -ItemType Directory -Force -Path "$Base\shared" | Out-Null
foreach ($w in "op-worker1","op-worker2") { & $VB storageattach $w --storagectl SATA --port 5 --device 0 --medium none }
foreach ($disk in @(@{n="asm1";gb=50;port=3}, @{n="asm2";gb=50;port=4}, @{n="vote1";gb=10;port=5})) {
  $f = "$Base\shared\$($disk.n).vdi"
  & $VB createmedium disk --filename $f --size ($disk.gb*1024) --variant Fixed
  & $VB modifymedium disk $f --type shareable
  foreach ($w in "op-worker1","op-worker2") { & $VB storageattach $w --storagectl SATA --port $disk.port --device 0 --type hdd --medium $f --mtype shareable }
}
foreach ($d in "vote1","asm1","asm2") { & $VB showmediuminfo disk "$Base\shared\$d.vdi" | Select-String '^(UUID|Location|Type|Capacity|In use by VMs):|op-worker' }

Check: for each of the three disks, Type: shareable, a Location under D:\VMs\rac-op\shared, the right Capacity (10240 MBytes for vote1, 51200 for the others), and both op-worker1 and op-worker2 under "In use by VMs".

4.1 What happens to each node, and why

Step op-controlplane op-worker1, op-worker2
a. Start and connect on 2205 yes yes
b. Name, identity, kubelet IP yes yes
c. Private NICs for Multus no: it has no NIC2/NIC3 yes
d, e. Data disks /var/lib/containers and /scratch no: it has only the OS disk yes
f. The operator's directories no yes (the same on both workers)
g. HugePages no: 2048 pages would lock all of its 4 GB yes
Move to its own address, then check it yes yes

Why each step:

  • Name, identity and kubelet IP: the host name becomes the Kubernetes node name. New SSH host keys replace the ones the seal removed. --node-ip matters on the workers, which have three NICs: without it the kubelet may advertise the wrong address, and pod traffic between nodes breaks.
  • Private NICs with no IP: enp0s8 and enp0s9 are only "parents" for Multus macvlan interfaces. Each RAC pod gets its own interface, IP (10.0.11.x and 10.0.12.x) and MAC address on top of them.
  • Promiscuous mode (accept-all-mac-addresses yes): this was the cause of the hardest network failure in the first build, 100% packet loss between pods. VirtualBox's "Allow All" setting only takes effect when the guest NIC itself is promiscuous. Otherwise the virtual NIC silently drops frames addressed to the pods' macvlan MACs.
  • Data disks chosen by size, not by name: Linux disk names (sdb, sdc...) do not follow VirtualBox port order. On worker2 in the manual lab's first build, /dev/sdc was a shared ASM disk, and formatting by name would have wiped the disk both nodes share. The ASM disks are 50 GB, so the sizes tell the disks apart. They're mounted by UUID for the same reason, and rsync -aAXH copies the images pulled in Phase 2 together with their SELinux labels.
  • The operator's directories with container_file_t: the operator mounts them into the RAC pods as hostPath volumes; their names follow its racHostSwLocation (/scratch/rac/cluster01) and racNodeName (racnode) settings. With SELinux enforcing, a container can only use host files with the container file label. semanage fcontext makes the label permanent.
  • HugePages: the database SGA goes into 2 MB hugepages, which are locked, never swapped and cheaper for the CPU to map. Kubernetes only gives hugepages to pods on nodes that reserved them: the RAC pods ask for hugepages-2Mi: 4Gi, so each worker reserves 2048 pages. The doc reserves 16384 (32 GB); this lab scales it to the 22 GB workers.
  • Moving the address last, in the background: changing the public IP cuts the SSH session you're typing in. A first attempt died halfway through for exactly that reason. So the change runs detached from your session and ends with a reboot.
  • ssh-keygen -R before connecting: every clone has its own host key but answers on the same port, 2205. Without the 0.2 SSH settings, SSH refuses the new key with "REMOTE HOST IDENTIFICATION HAS CHANGED"; removing the old entry avoids that.

6.1 Why RAC needs Multus

A Kubernetes pod normally has exactly one network interface, eth0, from the cluster network (Flannel here). RAC needs more than that:

  • A public network: client connections, the VIPs and SCAN. That's eth0.
  • A private interconnect: dedicated, low-latency and not routed through the cluster network. Cache Fusion moves database blocks between the instances over it, and the cluster heartbeat runs on it. If the heartbeat is lost, Grid evicts a node.

Multus is a "meta" CNI plugin that attaches additional networks to a pod. Each extra network is described by a NetworkAttachmentDefinition (NAD). This lab uses macvlan, which gives the pod its own MAC address directly on the worker's enp0s8 / enp0s9. Two networks give Grid's HAIP (highly available IP) two paths, so the interconnect survives losing one.

9.2 The database password, encrypted (op-controlplane)

What happens to the password: you type it twice at a hidden prompt. It lives only in a shell variable, is piped straight into OpenSSL, and is encrypted with a new RSA key; the variable is then cleared. It's never written to a file, the screen or this guide. The -pkeyopt settings are the operator's default (rsa_padding_mode:oaep;rsa_oaep_md:sha256;rsa_mgf1_md:sha256), which the RacDatabase names again in Phase 11.

Phase 12Access from Windows

Result of this phase: a client on the Windows PC connects through SCAN (127.0.0.1:31521/orclpdbsvc), is sent on to either instance, and reconnects to the other instance when one goes away.

How a RAC connection works, and why it fails from Windows today:

  1. The client connects to a SCAN listener (LISTENER_SCAN1 or 2, port 1521).
  2. The SCAN listener picks an instance offering the service and redirects the client to that instance's node listener, using the address the instance registered: its local_listener.
  3. The client opens a second connection to that address.

Inside the cluster all three steps work. Why not the operator's NodePort option: the RacDatabase fields for node-listener NodePorts (baseLsnrTargetPort) only take effect when the database is first created; this cluster already exists, so the same result is set up by hand here. 12.5 Connect from Windows through SCAN

What: a small Python script opens 10 connections to 127.0.0.1:31521/orclpdbsvc and prints, for each, which instance, host and container served it.

Why it proves the whole path: each connection goes Windows → forward 31521 → LISTENER_SCAN1 → redirect to racnode1-0-vip…:31522 or racnode2-0-vip…:31523 → Windows hosts (127.0.0.1) → that forward → that instance's node listener. A line with an instance name has passed every step.

The password: asked at a hidden prompt (getpass); it isn't written to the file, the screen or the history. It's the database password from Phase 9, which DBCA used for SYS, SYSTEM and the PDB admin.

Driver: python-oracledb in thin mode needs no Oracle client. Thin mode has no TAF, so failover here means a new connection lands on the surviving instance (12.6), not a session that survives unchanged.

PowerShell on the Windows PC
@'
import collections, getpass, oracledb

DSN = "127.0.0.1:31521/orclpdbsvc"
SQL = """select sys_context('USERENV','INSTANCE_NAME'),
                sys_context('USERENV','SERVER_HOST'),
                sys_context('USERENV','CON_NAME') from dual"""

pw = getpass.getpass("SYSTEM password: ")

for n in range(1, 11):
    with oracledb.connect(user="system", password=pw, dsn=DSN) as conn:
        with conn.cursor() as cur:

    print(f"{n:2}  {inst:9} {host:11} {con}")
print("oracledb", oracledb.__version__, "thin mode:", oracledb.is_thin_mode())

What, in three parts:

  • a. (op-controlplane) read the RAC pods' health probes; restart the node listeners again as in 12.2 and check that local_listener keeps the values from 12.3; take orclpdbsvc off ORCLCDB1.
  • b. (Windows) run the test script: every connection should now land on ORCLCDB2.

Why the service and not the whole instance: for new connections, stopping the service on one instance has the effect of losing that instance (SCAN stops sending clients there), without touching the database. Part a also reads the pods' probes first, to know whether stopping an instance could make Kubernetes restart a pod.

Interruption: a few seconds per node for the listener restart (as in 12.2). Without -force, stopping the service on ORCLCDB1 leaves existing sessions there running; only new connections go to ORCLCDB2.

Open points:

  • Which image (settled). The manual lab's image can't be reused: it was built from the OCNE doc's short Containerfile, and the operator drives the setup through the scripts in Oracle's own RAC image (it follows /tmp/orod/oracle_db_setup.log).   • Sizing (settled in 11.1). 16 GiB pods with 4 GiB of hugepages fit once the operator runs one controller pod instead of three; the RAC_WEBHOOK_DEV_MODE way around the 16 GiB minimum isn't needed.
  • Platform. The operator's README lists OKE, OpenShift and OLCNE 1.9+ as tested, and GKE, AKS, EKS, OKD and Minikube as supported. That table covers the whole operator; the RAC controller's own prerequisites are written only for OCNE. A plain kubeadm cluster with CRI-O isn't on either list, so expect lab-specific workarounds, as in the manual lab. One showed up so far: the ASM discovery string with by-id disk names (CRS_ASM_DISCOVERY_STRING in 11.2, recovery in 11.4).
  • Online redo logs land in FRA. With no DBREDO disk group in the YAML, the setup script sets DB_CREATE_ONLINE_LOG_DEST_1 to the recovery disk group, so the redo logs are only in +FRA (one member per group). That works for the lab; the usual layout keeps redo on DATA or its own disk group with a second member in FRA. The control file too ended up only in +FRA (11.5). 11.6 adds a second copy of each in +DATA. db_recovery_file_dest_size isn't set by the operator; DBCA chose 23895M.
  • Access from outside is set up by hand (Phase 12). The operator's own node-listener NodePort fields (baseLsnrTargetPort) only apply when the database is first created.   • VIPs are the pod IPs. Flannel gives each pod one IP, so racnode1-0-vip and racnode2-0-vip resolve to the pods' own addresses. A VIP can't move to the other node when its pod dies; client failover relies on SCAN and the service running on the other instance.
