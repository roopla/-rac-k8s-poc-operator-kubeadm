Oracle RAC 19c on Kubernetes with Oracle's Database Operator

How a two-node RAC database runs on a three-node kubeadm cluster in VirtualBox: the components, the networks, the shared storage, what the operator does, and the order in which it all comes up.

1What this system is

A two-node Oracle RAC 19c database (Release Update 19.32) running in two Kubernetes pods. The Kubernetes cluster is built with kubeadm on three VirtualBox VMs on a single Windows PC. Oracle's Database Operator creates and watches the database: you describe the database in one RacDatabase YAML file, and the operator turns it into the pods, volumes and network names, then lets Oracle's own setup scripts inside the pods install Grid Infrastructure and create the database.

2The whole system

Layer by layer:

  • Windows PC. Hosts VirtualBox and is the only way in: SSH and the Kubernetes API reach the VMs through port forwards on the VirtualBox NAT Network (127.0.0.1:2220–2222 for SSH, :6444 for kubectl). The VM disks, including the three shared ASM disks, are files on D:.
  • op-controlplane. Runs the Kubernetes control plane: the API server (every change goes through it), etcd (where all objects are stored), the scheduler (picks a node for each pod) and the controller manager (makes StatefulSets create their pods). CoreDNS answers the RAC host names. No database runs here.
  • op-worker1 and op-worker2. Each runs one RAC pod. A pod here behaves like a small RAC server: systemd runs inside it, and Grid Infrastructure, ASM, the listeners and one database instance all live in the same container. The pods are Guaranteed (requests equal limits), so Kubernetes never squeezes their memory.
  • The operator. One controller pod that watches the RacDatabase object. It runs on whichever worker Kubernetes chose; it doesn't need to be near the database.
  • Shared ASM disks. The same three disks are attached to both worker VMs, so both pods see the same blocks. That's what makes it a RAC cluster rather than two separate databases.
  • Kubernetes objects. You create four things (the RacDatabase, two Secrets, two network definitions, a node label); the operator creates the rest.

Why two private lines between the pods: RAC nodes constantly exchange heartbeats and data blocks (the interconnect). Two separate private networks give Grid two paths, so the cluster survives the loss of one.

3Networks

Every RAC node needs one public network (clients, SCAN, VIPs) and at least one private network (the interconnect). In Kubernetes a pod normally has only one interface, so the design uses two network plugins:

  • Flannel gives each pod its normal interface, eth0, on the pod network 10.244.0.0/16. Each node gets its own /24 (10.244.1.0/24 on op-worker1, 10.244.2.0/24 on op-worker2), and Flannel tunnels between nodes with VXLAN. The two pods are therefore on *different* /24s; Oracle's setup script registers the public network as 10.244.0.0 with mask 255.255.0.0 so Grid sees one public subnet.
  • Multus lets a pod have extra interfaces, described by NetworkAttachmentDefinitions (macvlan-conf1, macvlan-conf2). Each one uses macvlan on a worker NIC that has no IP of its own (enp0s8, enp0s9): the pod's eth1 and eth2 get their own MAC and IP (10.0.11.x, 10.0.12.x) directly on the VirtualBox internal networks op-priv1 and op-priv2. Promiscuous mode on those VirtualBox NICs must be Allow All, or the extra MAC addresses are dropped.

Names instead of addresses. The operator creates headless Services (Services without a virtual IP), so CoreDNS returns the pod's own IP for racnode1-0, racnode2-0, their -vip names, and both pod IPs for racnode-scan. Grid is installed against these names, so a pod that is recreated with a new IP keeps working.

VIPs are the pod IPs. On a classic RAC each node has a spare virtual IP that moves to the other node on failure. A Flannel pod has exactly one IP, so here racnodeN-0-vip resolves to the pod itself; when a pod dies, its VIP dies with it. Clients still fail over through SCAN and the service running on the other instance.

From outside the cluster (Windows). A RAC client connects in two steps: first to a SCAN listener, which then redirects it to the node listener of the instance it picks, at the address that instance registered (local_listener). Out of the box both steps use addresses only the cluster can reach: SCAN on 1521 behind the operator's NodePort racnode-scan-lsnr (31521), and node listeners on the pod IPs, port 1522. So the redirect address was changed so that the pods and Windows can both reach it:

Each node gets its own port because the port SCAN hands out must be the same number on Windows, on the NodePort and on the listener, and Windows reaches both nodes through the one address 127.0.0.1. Once local_listener is set explicitly, Grid's agent stops rewriting it (it rewrote it when the listener's ports changed, and left it alone after). A client on Windows then connects to 127.0.0.1:31521/orclpdbsvc and lands on either instance.

4Storage

Shared disks. Each shared disk is a fixed-size, shareable VDI file attached to both worker VMs on the same SATA port. VirtualBox gives the disk a serial number derived from the VDI's UUID, so Linux shows it under the same /dev/disk/by-id/ata-VBOX_HARDDISK_VB… name on both workers. Those names, not /dev/sdX, go into the RacDatabase, because sdX letters depend on discovery order.

From disk to ASM. The operator first runs a short-lived disk-check pod on each worker to read every disk's size, then creates one PersistentVolume (block mode, ReadWriteMany) and one PersistentVolumeClaim per disk, and hands the device to both pods at the same path. Inside the pods, ASM builds one disk group per disk:

Disk groupType in the YAMLHolds
+VOTEDG (10 GB)CRSDGthe cluster registry (OCR), the voting file, ASM's spfile and password file; created by Grid's root.sh
+DATA (50 GB)DBDATAFILESDGdata files, the database spfile, control file copy 1, one member of each redo group
+FRA (50 GB)DBRECOVERYthe fast recovery area: archived logs, control file copy 2, the second member of each redo group; limit 23895M

Why three disk groups: the cluster's own files stay small and separate from the database, and a full recovery area can't take the cluster down with it. Each disk group has one disk and EXTERNAL redundancy, because in this lab there is nothing to mirror to: every disk is a file on the same D: drive.

Not shared: each worker's /scratch disk holds that node's Oracle homes (mounted as /u01 in the pod) and the staged gold-image zips; /var/lib/containers holds the container image. The homes are per node: each pod unzips and installs its own copy.

5How the operator builds it

An operator is a program that runs inside Kubernetes and adds a new kind of object, here RacDatabase, together with the logic to make it real. Kubernetes stores your RacDatabase like any other object; the operator notices it and keeps creating or fixing ordinary objects until the cluster matches what you asked for. This loop is called reconciling.

  • Admission webhook. Before the API server stores the object, it asks the operator's webhook. The webhook refuses settings that can't work, such as less than 16 GiB of pod memory, too few hugepages for the SGA, or missing disk groups. Kubernetes only calls webhooks over TLS; cert-manager issues that certificate.
  • Reconcile steps. Disk check, volumes, Services and StatefulSets, in that order. Each RAC node gets its own StatefulSet with one pod, so racnode1-0 and racnode2-0 keep stable names and their own volumes across restarts.
  • Configuration as environment. The operator translates the YAML into environment variables for the pods: the device lists per disk group, the disk group names, database name, SGA and PGA, plus your own envVars. The SSH keys and the encrypted password arrive as mounted Secrets; the password is decrypted only inside the pod, at install time.
  • The install itself runs in the pods. The pod starts systemd, which runs Oracle's setup scripts (runOracle.sh → main.py). Both pods prepare themselves; racnode1-0 is the install node and drives every installer step on both pods over SSH. The operator only watches and reports.
  • Status. The operator reads the pods and the database back into the RacDatabase status: PENDING during the install, then OPEN … AVAILABLE with the connect string racnode-scan:1521/orclpdbsvc.

The software: gold-image zips, patched once

Why gold images: a RAC pod only unzips the Grid and DB homes and registers them with software-only installs (-noCopy). If the zips were plain 19.3, every deployment would also have to replace OPatch and apply the Release Update on both nodes, adding a long patching step to an install that already takes hours. Instead the homes are patched once per RU on a separate Oracle Linux 9.8 server, installed software-only there, and packed with -createGoldImage. Every RAC build at that patch level reuses the two zips.

What goes into each home (the build on oldblab-db1, 28 October 2026, RU 19.33.0.0.261020):

HomePatches after the build (opatch lspatches)
GridGI RU 39922757, which brings Database RU 39915792, OCW 39922783, ACFS 39922802, Tomcat 39107855, DBWLM 39107825; plus OJVM RU 39803650 and JDK 39902051
DBGI RU 39922757, which brings Database RU 39915792 and OCW 39922783; plus OJVM RU 39803650 and JDK 39902051

Why the GI RU in the DB home too: it contains the Database RU and the OCW RU that a RAC database home needs, so both homes end up at exactly the same level. The OJVM RU is only needed in the DB home; this build also put it in the Grid home, which did no harm. Next time it goes into the DB home only, as a one-off after the RU.

Why it is quick to deploy: -applyRU patches the unzipped home before the installer runs, so the software-only install already uses the patched 19.33 installer, which knows Oracle Linux 9. The gold image is the home after that install: patched and relinked, not configured. In the pod, the operator's setup script unzips it and registers it again with -noCopy, and DBCA brings the new database's dictionary to the same patch level.

The image the pods run: the RAC slim image

What it is: Oracle Linux 9 with the OS packages, users and groups Oracle needs, plus Oracle's own setup scripts (runOracle.sh, main.py and the modules they call), but no Oracle software. That is what "slim" means. The operator starts this image and the scripts in it install Grid and the database at run time, from the gold-image zips staged on the worker, into /u01 on the worker's disk. The image stays small (443 MB) and the 11 GB homes live outside it.

Why on each worker, with no registry: each worker's CRI-O can only start images it has locally, and either RAC pod may land on either labelled worker. Podman builds straight into the image store CRI-O reads (/var/lib/containers), so the image never has to leave the worker it was built on.

Why each part of the build:

  • podman-docker: Oracle's build script calls docker; this package makes docker run Podman. /etc/containers/nodocker silences its "emulating docker" notice.
  • A sparse clone: only the RAC folder of Oracle's large docker-images repository is downloaded.
  • -v 19.3.0: the 19c folder, used for every 19c Release Update, 19.32 included. Its Containerfile is based on Oracle Linux 9.
  • -i: skip the checksum of install zips, since the slim image doesn't contain any.
  • --build-arg SLIMMING=true: build without the Oracle software.
  • TMPDIR on /scratch: Podman's temporary files go to the 80 GB disk instead of the small root disk.
  • crictl images: if CRI-O lists the image, Kubernetes can start it.

The build downloads Oracle Linux packages; here it took under 3 minutes per worker (allow 10–20 on a slower connection). The two workers can build at the same time, in two windows.

6The install sequence

Each node builds its own homes. The gold-image zips are staged on both workers, so each pod unzips Grid and the database home itself, and every installer runs with -noCopy: nothing is copied between nodes. The software-only installs register and relink each home in place; then one cluster configuration run on racnode1-0 creates the cluster, and root.sh on each node starts Clusterware there (VOTEDG is created on the first node).

Where the time goes: the unzips (about 22 GB written by two pods at once) and DBCA. Both are bound by the one physical drive under all the VM disks; the actual Grid and database installs take under 30 minutes together.

The red bar is the one stop in this run: ASM couldn't see the DATA and FRA disks (ORA-15014) because the setup script had guessed a disk pattern from the vote disk's name. Widening the discovery string and rerunning the setup script resumed the install where it stopped; the YAML now sets CRS_ASM_DISCOVERY_STRING so a new build doesn't stop there.

Limits of this design:

  • One physical drive. All VM disks, shared or not, are files on D:. EXTERNAL redundancy and the control-file copies protect against a lost disk group, not a lost drive, and the drive is the bottleneck (the alert log reports slow redo writes).
  • VIPs can't move. A VIP is its pod's own IP, so client failover relies on SCAN and services, not on VIP relocation.
  • Access from outside is hand-made. The operator can publish node listeners as NodePorts (baseLsnrTargetPort) only when the database is first created; here the extra listener ports, the explicit local_listener, the NodePorts and the Windows forwards were added afterwards (section 3). A new build should use the operator's fields instead.
  • Restarts depend on a guard. Grid's local files (/etc/oracle, the ohasd unit) live in the container; on every start Oracle's setup script restores them with rootcrs.sh -updateosfiles and starts Clusterware, which moves the VIPs and SCAN to the pods' new IPs. Without SKIP_DBCA=true in the env ConfigMaps the same script would go on to DBCA whenever an instance isn't open yet; with it, a restart of both pods came back without help (lab guide, Phase 13).
  • Stopping the lab: crsctl stop crs, not srvctl stop database. A shutdown and cold start of all three VMs came back without a manual step, in about 12 minutes from VM start to both instances open (lab guide, Phase 14). That needs the database's Clusterware target to stay ONLINE: srvctl stop database sets it to OFFLINE, and the database then stays down after the start. Kubernetes gives a pod only 30 s to stop, too short for RAC, so Clusterware is stopped by hand before the VMs. A hard power-off hasn't been tested.
  • SCAN from outside goes through one pod. The operator's racnode-scan-lsnr Service has one endpoint, racnode1-0's SCAN listener, so Windows can't reach SCAN while racnode1-0 is down, although the other instance is open.
  • Configuration changes restart the whole cluster. The operator keeps a hash of each env ConfigMap in the pod template, so changing one rolls both RAC pods together, stopped within 30 s with the database open. envVars changes don't reach an existing database at all for this spec style.
  • No session failover in thin mode. python-oracledb thin has no TAF: when an instance or its service goes away, a new connection lands on the other instance, but an open session doesn't move.
  • Platform. Oracle documents the RAC controller for Oracle Cloud Native Environment. A kubeadm cluster with CRI-O on VirtualBox works, as this build shows, but is not a supported production platform.
