How to use this guide

This guide builds a second lab, the operator lab, next to the manual lab you already have. It follows the manual guide's Phases 0 and 3–6 step by step, with its own names, addresses and ports, so the two labs never overwrite each other. The RAC database itself will come from Oracle's database operator in the later phases, instead of the hand-run installs of the manual lab's Phases 8–14.

Copy every block exactly as it is. Each block's label says where it runs, and the connect line shows how to get there. Blocks labelled # PowerShell run in a PowerShell window on your PC, never in Git Bash.

One lab at a time. Each lab needs about 48 GB of the PC's 64 GB, and both use the same NAT Network. Before you start the operator lab, the manual lab must be powered off, and the other way round:

Phase 0Windows host and the operator lab's port forwards

Result of this phase: a clean starting point for the operator lab, the PC checked for room, and SSH port forwards 2220–2222 on the shared k8s-public network. The manual lab and the golden VM are not touched.

0.0 Start clean (only if you built the operator lab before)

What: removes an earlier operator lab: the VMs op-controlplane, op-worker1, op-worker2, the folder D:\VMs\rac-op with all its disks, the operator lab's port-forward rules, and the SSH host keys remembered for ports 2220–2222. On a first build it just reports that there's nothing to remove.

What it never touches: ol98-golden, controlplane, worker1, worker2, D:\VMs\rac-poc and the k8s-public network itself. Every name in the block starts with op- or rac-op.

PowerShell
$VB = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"; $Base = "D:\VMs\rac-op"
$existing = (& $VB list vms) -join "`n"
foreach ($v in "op-worker1","op-worker2","op-controlplane") {
  if ($existing -match ('"' + $v + '"')) { & $VB controlvm $v poweroff 2>$null; Start-Sleep 3; & $VB unregistervm $v --delete; "removed VM $v" }
}
$left = (& $VB list hdds) | Select-String '^Location:\s+(.*)$' | ForEach-Object { $_.Matches[0].Groups[1].Value } | Where-Object { $_ -like "$Base\*" }
foreach ($d in $left) { & $VB closemedium disk $d --delete; "removed disk $d" }
if (Test-Path $Base) { Remove-Item $Base -Recurse -Force; "removed folder $Base" }
foreach ($r in "ssh-opcp","ssh-opw1","ssh-opw2","k8sapi-op") { & $VB natnetwork modify --netname k8s-public --port-forward-4 delete $r 2>$null }
foreach ($f in "$env:USERPROFILE\.ssh\known_hosts", "$env:USERPROFILE\.ssh\known_hosts_rac_lab") {
  if (Test-Path $f) { foreach ($p in 2220, 2221, 2222) { ssh-keygen -R "[127.0.0.1]:$p" -f $f 2>$null | Out-Null } }
}
"--- VMs (the manual lab and ol98-golden must still be listed; no op-*) ---"
& $VB list vms

Check: list vms still shows ol98-golden, controlplane, worker1 and worker2, and no op-* VM.

Why: the operator lab needs the same memory and CPU as the manual lab, about 48 GB, so only one lab can run at a time. On disk it needs its own room: three fixed ASM disks (110 GB together) are written in full straight away, and the workers' disks grow as they fill.

0.3 Port forwards for the operator lab

What: three SSH forwards on the existing k8s-public network: 2220 → op-controlplane, 2221 → op-worker1, 2222 → op-worker2. The golden VM's forward, 2205 → 10.0.1.5, is already there and is reused for personalising the clones in Phase 4.

Why on the same network: the two labs never run at the same time, so they can share k8s-public and its NAT. Different IPs (.20–.22) and different ports keep them apart; the rule names start with ssh-op so 0.0 can remove exactly these.

& $VB natnetwork modify --netname k8s-public --port-forward-4 "ssh-opcp:tcp:[]:2220:[10.0.1.20]:22"
& $VB natnetwork modify --netname k8s-public --port-forward-4 "ssh-opw1:tcp:[]:2221:[10.0.1.21]:22"
& $VB natnetwork modify --netname k8s-public --port-forward-4 "ssh-opw2:tcp:[]:2222:[10.0.1.22]:22"
& $VB natnetwork list

Check: natnetwork list shows k8s-public with the manual lab's rules (ssh-golden, ssh-cp, ssh-w1, ssh-w2, and any NodePort rules) plus ssh-opcp, ssh-opw1 and ssh-opw2. If a line says the rule already exists, it was added before; that's fine.

Phase 3Clone the three operator-lab nodes

Result of this phase: three VMs (op-controlplane, op-worker1, op-worker2) cloned from the same golden image as the manual lab, the workers with two data disks each and their private NICs on op-priv1 / op-priv2, and three new disks that both workers share for ASM: 10 GB for VOTEDG, 50 GB each for DATA and FRA.

3.1 Check that the golden VM is still sealed

Why: clones must come from the sealed golden image: no machine ID, no SSH host keys. You sealed it before cloning the manual lab. If the golden VM has been started since then, it has made itself a new machine ID and host keys, and every clone would share them. Kubernetes refuses to join nodes with the same machine ID.

How to tell without starting it: VirtualBox records when a VM last changed state. If the golden VM's last change (its power-off after sealing) is older than the manual lab's clones, nobody has started it since.

PowerShell
$VB = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"; $g = "ol98-golden"
$info = & $VB showvminfo $g --machinereadable
$state = ($info | Select-String '^VMState="(.*)"').Matches[0].Groups[1].Value
$raw = ($info | Select-String '^VMStateChangeTime="(.*)"').Matches[0].Groups[1].Value
$changed = [datetime]::SpecifyKind([datetime]::ParseExact($raw.Substring(0,19), 'yyyy-MM-ddTHH:mm:ss', $null), 'Utc')   # VirtualBox writes UTC
$cpCfg = (& $VB showvminfo controlplane --machinereadable | Select-String '^CfgFile="(.*)"').Matches[0].Groups[1].Value
$cloned = (Get-Item (Split-Path $cpCfg)).CreationTimeUtc   # when the manual lab's controlplane was cloned
"manual lab folder:    $(Split-Path $cpCfg)"
"golden state:         $state"
"golden last changed:  $($changed.ToString('u'))"
"manual lab cloned:    $($cloned.ToString('u'))"
if ($state -eq 'poweroff' -and $changed -lt $cloned) { "OK: still sealed, not started since the manual lab was cloned" } else { "STOP: golden VM was started after the seal; reseal it (below)" }
& $VB snapshot $g list

Check: the line says OK: still sealed…, and the snapshot list shows the pre-seal snapshot. Then go straight to 3.2. The block finds the manual lab's folder from VirtualBox itself, wherever it is on your disk.

Only if it says STOP: seal it again, in place. Don't restore the pre-seal snapshot: fixes made to the golden image after that snapshot would be lost. Starting the golden VM gives it a new machine ID and host keys for a moment; the seal block removes them again and powers it off.

ssh-keygen -R "[127.0.0.1]:2205" 2>$null

If SSH warns that the host key for port 2205 has changed, run ssh-keygen -R "[127.0.0.1]:2205" in PowerShell and connect again.

3.2 Clone and size the nodes

Why these sizes: the same as the manual lab. op-controlplane gets 2 vCPU and 4 GB with no private NICs; each worker gets 4 vCPU and 22 GB, an 80 GB disk for /scratch and a 100 GB disk for /var/lib/containers.

What's different: the workers' second and third NICs move from the manual lab's internal networks rac-priv1 / rac-priv2 to the operator lab's op-priv1 / op-priv2. The clones inherit the golden VM's NIC settings, including the "Allow All" promiscuous mode Multus needs; only the network names change.

PowerShell
$VB = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"; $Base = "D:\VMs\rac-op"; $g = "ol98-golden"
while ("$(& $VB showvminfo $g --machinereadable | Select-String '^VMState=')" -notmatch 'poweroff') { Start-Sleep 3 }
foreach ($n in "op-controlplane","op-worker1","op-worker2") { & $VB clonevm $g --name $n --basefolder $Base --mode machine --register }
& $VB modifyvm op-controlplane --cpus 2 --memory 4096 --nic2 none --nic3 none
foreach ($w in "op-worker1","op-worker2") {
  & $VB modifyvm $w --cpus 4 --memory 22528 --intnet2 op-priv1 --intnet3 op-priv2
  & $VB createmedium disk --filename "$Base\$w\$w-scratch.vdi" --size 81920 --variant Standard
  & $VB createmedium disk --filename "$Base\$w\$w-containers.vdi" --size 102400 --variant Standard
  & $VB storageattach $w --storagectl SATA --port 1 --device 0 --type hdd --medium "$Base\$w\$w-scratch.vdi"
  & $VB storageattach $w --storagectl SATA --port 2 --device 0 --type hdd --medium "$Base\$w\$w-containers.vdi"
}
foreach ($n in "op-controlplane","op-worker1","op-worker2") { "--- $n"; & $VB showvminfo $n --machinereadable | Select-String '^(cpus|memory|nic[123]|nat-network1|intnet[23])='; & $VB showvminfo $n | Select-String '^NIC [23]:' }

Check:

  • op-controlplane: cpus=2, memory=4096, nic1="natnetwork" with nat-network1="k8s-public", and nic2="none", nic3="none";
  • each worker: cpus=4, memory=22528, nat-network1="k8s-public", intnet2="op-priv1", intnet3="op-priv2", and two NIC 2: / NIC 3: lines that include Promisc Policy: allow-all, each with its own MAC address. (The machine-readable output has no promiscuous-mode line on this VirtualBox version, so the check reads it from the normal output.)

3.3 The shared ASM disks

What: three disks attached to both workers at once, one per ASM disk group:

Disk Size SATA port Disk group Holds
vote1.vdi 10 GB 5 VOTEDG the cluster's own files: voting file, OCR, the ASM password file and spfile
asm1.vdi 50 GB 3 DATA the database's data files, control files and redo logs
asm2.vdi 50 GB 4 FRA the fast recovery area: archived logs, flashback logs, backups

Why three disk groups instead of one: keeping the cluster's files apart from the database makes each easier to size, move and repair; a full FRA can't stop the cluster, and the clusterware disk group stays small. The manual lab put everything into one DATA disk group.

Why port 5: the SATA controller has six ports (0–5). Port 5 carries the golden VM's empty DVD drive, which the clones inherited and nothing uses; the block removes it and puts vote1 there.

Why fixed size and shareable: RAC is a shared-disk database, so both nodes need the same block devices; VirtualBox only allows the shareable type on fixed-size disks, and without it refuses to attach the second VM. These are new, empty disks in D:\VMs\rac-op\shared; the manual lab's disks stay with the manual lab. Don't snapshot the workers: VirtualBox can't snapshot a VM with shareable disks. Creating the fixed disks takes a few minutes.

PowerShell
$VB = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"; $Base = "D:\VMs\rac-op"
New-Item -ItemType Directory -Force -Path "$Base\shared" | Out-Null
foreach ($w in "op-worker1","op-worker2") { & $VB storageattach $w --storagectl SATA --port 5 --device 0 --medium none }
foreach ($disk in @(@{n="asm1";gb=50;port=3}, @{n="asm2";gb=50;port=4}, @{n="vote1";gb=10;port=5})) {
  $f = "$Base\shared\$($disk.n).vdi"
  & $VB createmedium disk --filename $f --size ($disk.gb*1024) --variant Fixed
  & $VB modifymedium disk $f --type shareable
  foreach ($w in "op-worker1","op-worker2") { & $VB storageattach $w --storagectl SATA --port $disk.port --device 0 --type hdd --medium $f --mtype shareable }
}
foreach ($d in "vote1","asm1","asm2") { & $VB showmediuminfo disk "$Base\shared\$d.vdi" | Select-String '^(UUID|Location|Type|Capacity|In use by VMs):|op-worker' }

Check: for each of the three disks, Type: shareable, a Location under D:\VMs\rac-op\shared, the right Capacity (10240 MBytes for vote1, 51200 for the others), and both op-worker1 and op-worker2 under "In use by VMs".

Phase 4Personalize each node

Result of this phase: each node has its own name and IP address. The workers also have their private NICs ready for Multus, /scratch and /var/lib/containers on their own disks, the operator's directories, and 4 GB of hugepages.

Do one node at a time, in the order op-controlplane, op-worker1, op-worker2. Every clone boots with the golden VM's address 10.0.1.5, and two clones running at once would fight over it. Each node has its own section below with every command written out for it: copy the blocks in order, without changing anything. Start the next node only after the previous one passes its last check.

4.1 What happens to each node, and why

Step op-controlplane op-worker1, op-worker2
a. Start and connect on 2205 yes yes
b. Name, identity, kubelet IP yes yes
c. Private NICs for Multus no: it has no NIC2/NIC3 yes
d, e. Data disks /var/lib/containers and /scratch no: it has only the OS disk yes
f. The operator's directories no yes (the same on both workers)
g. HugePages no: 2048 pages would lock all of its 4 GB yes
Move to its own address, then check it yes yes

Why each step:

  • Name, identity and kubelet IP: the host name becomes the Kubernetes node name. New SSH host keys replace the ones the seal removed. --node-ip matters on the workers, which have three NICs: without it the kubelet may advertise the wrong address, and pod traffic between nodes breaks.
  • Private NICs with no IP: enp0s8 and enp0s9 are only "parents" for Multus macvlan interfaces. Each RAC pod gets its own interface, IP (10.0.11.x and 10.0.12.x) and MAC address on top of them.
  • Promiscuous mode (accept-all-mac-addresses yes): this was the cause of the hardest network failure in the first build, 100% packet loss between pods. VirtualBox's "Allow All" setting only takes effect when the guest NIC itself is promiscuous. Otherwise the virtual NIC silently drops frames addressed to the pods' macvlan MACs.
  • Data disks chosen by size, not by name: Linux disk names (sdb, sdc...) do not follow VirtualBox port order. On worker2 in the manual lab's first build, /dev/sdc was a shared ASM disk, and formatting by name would have wiped the disk both nodes share. The ASM disks are 50 GB, so the sizes tell the disks apart. They're mounted by UUID for the same reason, and rsync -aAXH copies the images pulled in Phase 2 together with their SELinux labels.
  • The operator's directories with container_file_t: the operator mounts them into the RAC pods as hostPath volumes; their names follow its racHostSwLocation (/scratch/rac/cluster01) and racNodeName (racnode) settings. With SELinux enforcing, a container can only use host files with the container file label. semanage fcontext makes the label permanent.
  • HugePages: the database SGA goes into 2 MB hugepages, which are locked, never swapped and cheaper for the CPU to map. Kubernetes only gives hugepages to pods on nodes that reserved them: the RAC pods ask for hugepages-2Mi: 4Gi, so each worker reserves 2048 pages. The doc reserves 16384 (32 GB); this lab scales it to the 22 GB workers.
  • Moving the address last, in the background: changing the public IP cuts the SSH session you're typing in. A first attempt died halfway through for exactly that reason. So the change runs detached from your session and ends with a reboot.
  • ssh-keygen -R before connecting: every clone has its own host key but answers on the same port, 2205. Without the 0.2 SSH settings, SSH refuses the new key with "REMOTE HOST IDENTIFICATION HAS CHANGED"; removing the old entry avoids that.

4.2 op-controlplane

c. Move to 10.0.1.20 and reboot (always last):

op-controlplane(still on 10.0.1.5; the session freezes or closes at the end)
Connect firstssh -p 2205 root@127.0.0.1
if [ "$(hostname)" = "op-controlplane" ]; then
cat >/root/set-ip.sh <<'EOF'
for u in $(nmcli -g UUID con show); do
  [ "$(nmcli -g connection.interface-name con show $u)" = "enp0s3" ] && nmcli con delete $u

nmcli con add type ethernet con-name pub ifname enp0s3 ipv4.method manual ipv4.addresses 10.0.1.20/24 \

EOF
setsid nohup bash /root/set-ip.sh >/root/set-ip.log 2>&1 </dev/null &
else echo "STOP: this VM is $(hostname), not op-controlplane; run step b first"; fi

Your SSH session freezes or closes. That's expected: the VM is moving to 10.0.1.20 and rebooting.

d. Check it on its own address (wait about a minute after the move):

PowerShell
ssh -p 2220 root@127.0.0.1 "hostname; ip -4 -br addr show enp0s3; ip -br link show enp0s8; df -h /scratch /var/lib/containers; grep HugePages_Total /proc/meminfo; systemctl is-active crio"

Check:

  • op-controlplane, and 10.0.1.20/24;
  • Device "enp0s8" does not exist and df: /scratch: No such file or directory: correct, it has no private NICs and no data disks;
  • /var/lib/containers is on the root filesystem (/dev/mapper/ol-root);
  • HugePages_Total: 0, and CRI-O is active.

d. Find the two data disks by size:

op-worker1(still on 10.0.1.5)
Connect firstssh -p 2205 root@127.0.0.1
lsblk -d -o NAME,SIZE,TYPE
pick() { lsblk -dbno NAME,SIZE,TYPE | awk -v lo=$(( ($1-2)*1024**3 )) -v hi=$(( ($1+2)*1024**3 )) '$3=="disk" && $2>=lo && $2<=hi {print "/dev/"$1}'; }

Phase 6Multus and the RAC private networks

Result of this phase: pods can have two extra interfaces, eth1 on 10.0.11.0/24 and eth2 on 10.0.12.0/24, with addresses you choose. A test between the workers proves the interconnect works before any Oracle software is involved.

6.1 Why RAC needs Multus

A Kubernetes pod normally has exactly one network interface, eth0, from the cluster network (Flannel here). RAC needs more than that:

  • A public network: client connections, the VIPs and SCAN. That's eth0.
  • A private interconnect: dedicated, low-latency and not routed through the cluster network. Cache Fusion moves database blocks between the instances over it, and the cluster heartbeat runs on it. If the heartbeat is lost, Grid evicts a node.

Multus is a "meta" CNI plugin that attaches additional networks to a pod. Each extra network is described by a NetworkAttachmentDefinition (NAD). This lab uses macvlan, which gives the pod its own MAC address directly on the worker's enp0s8 / enp0s9. Two networks give Grid's HAIP (highly available IP) two paths, so the interconnect survives losing one.

8.1 Build the slim image (op-worker1, then op-worker2)

What the slim image is: Oracle Linux 9 with the OS packages, users and groups Oracle needs, plus Oracle's own setup scripts, but no Oracle software. The operator starts this image and drives the scripts in it; they install Grid and the database from the zips in 8.2 into /u01, on the worker's disk. That's why the manual lab's image, built from the OCNE doc's short Containerfile, can't be used here: it doesn't have those scripts.

Why each line:

  • podman-docker: Oracle's build script calls docker. This package makes docker run Podman, which writes into the same image store CRI-O reads (/var/lib/containers). /etc/containers/nodocker silences its "emulating docker" notice.
  • A sparse clone: only Oracle's RAC folder of the large docker-images repository is downloaded.
  • -v 19.3.0: the 19c folder, which the README says to use for all 19c builds, RUs such as 19.32 included. Its Containerfile uses Oracle Linux 9.
  • -i: skip the checksum of install zips; the slim image doesn't contain any.
  • SLIMMING=true: build without the Oracle software.
  • TMPDIR on /scratch: Podman's temporary files go to the 80 GB disk instead of the small root disk.

The build downloads Oracle Linux packages and takes about 10–20 minutes. You can run it in op-worker1 and op-worker2 at the same time, in two windows.

8.2 Stage the gold-image zips (from the PC)

What: both 19.32 gold-image zips copied from C:\Users\alpoo\Downloads\oracle-stage to /scratch/software/stage on both workers, then checked against the PC's own checksums.

Why each part:

  • Both workers: the operator installs from the stage directory of the worker each RAC pod runs on, and either pod may land on either worker. It mounts the directory as hostSwStageLocation.
  • Zipped, not unpacked: the operator unzips them itself; the RacDatabase names them in gridSwZipFile and dbSwZipFile. Oracle's prerequisites accept a 19.28 or later gold image, and these are 19.32.
  • Mode 755: the permissions Oracle's prerequisites ask for on the zips.
  • restorecon: gives the files the container_file_t label set up in 4f, so the pods may read them under SELinux.
  • Checksums: 9.6 GB through a NAT port forward is easy to cut short. sha256sum -c on each worker compares against the checksums taken on the PC; a truncated or damaged copy fails here instead of an hour into the Grid install.

The copy takes a few minutes per worker. The checksums take about a minute on each side.

Git Bash
cd ~/Downloads/oracle-stage
sha256sum oracle-gridhome-19.32.zip oracle-dbhome-19.32.zip | tee /tmp/zips.sha256
for p in 2221 2222; do for f in oracle-gridhome-19.32.zip oracle-dbhome-19.32.zip; do
  for try in 1 2 3; do
    echo "--- port $p: $f (try $try)"
    scp -P $p $f root@127.0.0.1:/scratch/software/stage/ && grep " \*$f$" /tmp/zips.sha256 | ssh -p $p root@127.0.0.1 "cd /scratch/software/stage && sha256sum -c" && break
  done
done; done
for p in 2221 2222; do echo "--- checking port $p"
  ssh -p $p root@127.0.0.1 "hostname; cd /scratch/software/stage && chmod 755 oracle-*.zip && restorecon -F oracle-*.zip && ls -lhZ oracle-*.zip && sha256sum -c" < /tmp/zips.sha256
done

Check: for op-worker1 and op-worker2, both zips listed with -rwxr-xr-x, about 4.8 G and container_file_t, and two lines ending in OK. Each file is checked right after its copy and copied again, up to three times, if the checksum doesn't match: a copy through the NAT port forward can drop just before the end (lost connection at 99%). A FAILED line in the final check means all three tries failed for that file; paste the output.

9.2 The database password, encrypted (op-controlplane)

What happens to the password: you type it twice at a hidden prompt. It lives only in a shell variable, is piped straight into OpenSSL, and is encrypted with a new RSA key; the variable is then cleared. It's never written to a file, the screen or this guide. The -pkeyopt settings are the operator's default (rsa_padding_mode:oaep;rsa_oaep_md:sha256;rsa_mgf1_md:sha256), which the RacDatabase names again in Phase 11.

Password rules: 8–30 characters with at least one upper-case letter, one lower-case letter and one digit, and only letters, digits, _, # and -. Those rules satisfy Oracle's password checks; leaving out quotes, spaces, @ and $ keeps them out of trouble in the operator's shell scripts.

op-controlplane(you type the password twice)
Connect firstssh -p 2220 root@127.0.0.1
cd /root/rac-op/secrets
while :; do
  read -rsp "Database password: " PW; echo; read -rsp "Same again: " PW2; echo
  if [ "$PW" != "$PW2" ]; then echo "They differ; try again."; continue; fi
  if [[ ${#PW} -ge 8 && ${#PW} -le 30 && "$PW" =~ [A-Z] && "$PW" =~ [a-z] && "$PW" =~ [0-9] && "$PW" =~ ^[A-Za-z0-9_#-]+$ ]]; then break; fi
  echo "8-30 characters, upper and lower case and a digit, only letters, digits, _ # -; try again."
done
rm -f key.pem key.pub pwdfile.enc
openssl genrsa -out key.pem 2>/dev/null && openssl rsa -in key.pem -pubout -out key.pub 2>/dev/null
printf '%s\n' "$PW" | openssl pkeyutl -encrypt -pubin -inkey key.pub -out pwdfile.enc \
  -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 -pkeyopt rsa_mgf1_md:sha256
LEN=$(( ${#PW} + 1 )); unset PW PW2
GOT=$(openssl pkeyutl -decrypt -inkey key.pem -in pwdfile.enc -pkeyopt rsa_padding_mode:oaep -pkeyopt rsa_oaep_md:sha256 -pkeyopt rsa_mgf1_md:sha256 | wc -c)
[ "$GOT" -eq "$LEN" ] && echo "OK: pwdfile.enc decrypts to the password you typed ($LEN bytes with the newline)" || echo "STOP: decrypt test failed"
chmod 600 key.pem pwdfile.enc
kubectl -n rac delete secret db-user-pass --ignore-not-found
kubectl -n rac create secret generic db-user-pass --from-file=pwdfile.enc --from-file=key.pem
kubectl -n rac get secret db-user-pass -o jsonpath='{.data}' | grep -o '"[a-z.]*"'

Check: OK: pwdfile.enc decrypts… (only the length is shown, never the password), then "key.pem" and "pwdfile.enc". Remember the password: it's the one for SYS, SYSTEM and the PDB admin when you connect in Phase 12.

Where the files stay: /root/rac-op/secrets on op-controlplane, readable only by root. To change the password later, run 9.2 again and recreate the database.

10.1 Find the disks' by-id names (from the PC)

Why by-id and not /dev/sdd: sdX letters depend on discovery order and can differ between the workers. The by-id name comes from the disk's serial number, which VirtualBox derives from the VDI's UUID, so it's the same on both workers.

The block looks up each disk's UUID, finds its by-id name on both workers, checks they match and that the disk is blank, and saves the three paths on op-controlplane as VOTE=, DATA= and FRA= lines in /root/rac-op/asm-disks for the RacDatabase.

PowerShell
$VB = "C:\Program Files\Oracle\VirtualBox\VBoxManage.exe"; $Base = "D:\VMs\rac-op"
$ASM = [ordered]@{}; $Disks = [ordered]@{VOTE="vote1"; DATA="asm1"; FRA="asm2"}
foreach ($d in $Disks.GetEnumerator()) {
  $pre = ((& $VB showmediuminfo disk "$Base\shared\$($d.Value).vdi") | Select-String '^UUID:\s+([0-9a-f]{8})').Matches[0].Groups[1].Value
  $w1 = ssh -p 2221 root@127.0.0.1 "ls /dev/disk/by-id/ | grep -v part | grep ^ata-VBOX_HARDDISK_VB$pre-"
  $w2 = ssh -p 2222 root@127.0.0.1 "ls /dev/disk/by-id/ | grep -v part | grep ^ata-VBOX_HARDDISK_VB$pre-"
  $blank = ssh -p 2221 root@127.0.0.1 "blkid -p /dev/disk/by-id/$w1 >/dev/null 2>&1 && echo used || echo blank"
  if ($w1 -and ($w1 -eq $w2) -and (@($w1).Count -eq 1)) { $ASM[$d.Key] = "/dev/disk/by-id/$w1"; "OK    $($d.Key) ($($d.Value)) = $w1 (same on both workers, $blank)" }
  else { "STOP  $($d.Key) ($($d.Value), VB$pre): op-worker1 sees '$w1', op-worker2 sees '$w2'" }
}
if ($ASM.Count -eq 3) {
  ($ASM.GetEnumerator() | ForEach-Object { "$($_.Key)=$($_.Value)" }) -join "`n" | ssh -p 2220 root@127.0.0.1 "tr -d '\r' > /root/rac-op/asm-disks; cat /root/rac-op/asm-disks"
}

Check: three OK lines (VOTE, DATA, FRA), each ending in blank, then the three VOTE=…, DATA=…, FRA=… lines as saved on op-controlplane. used instead of blank means the disk carries a signature from earlier use; ASM refuses such disks, so stop and paste the output.

11.2 Write and check the RacDatabase (op-controlplane)

What each part maps to (the manual lab step it replaces in brackets):

  • instanceDetails: 2 nodes named racnode1-0 / racnode2-0, Oracle homes under /scratch/rac/cluster01/racnode<n> (manual 4f, 10.4), private interfaces eth1 / eth2 from the two Multus networks (6.3), on workers labelled raccluster=raccluster01 (5.4).
  • envVars: the setup log in /tmp/orod, and IGNORE_CRS_PREREQS / IGNORE_DB_PREREQS: in a container on VirtualBox some optional prerequisite checks always fail (no swap, /dev/shm as tmpfs), as the manual lab's INS-13014 warnings showed (manual 11.4).
  • CRS_ASM_DISCOVERY_STRING: the list of disks ASM may look at (its asm_diskstring). Without it the install fails at the DATA/FRA step (see 11.4): Oracle's setup script builds the discovery string from the first CRSDG disk only, by cutting the last 2 characters of its path and adding *. That works for names like /dev/sdd → /dev/sd*, but each by-id name starts with its own UUID, so only the vote disk would match. Listing all three paths lets ASM see every disk from the start.
  • asmDiskGroupDetails: three disk groups, each on one disk from 10.1 and with external redundancy (VirtualBox is the only copy anyway): VOTEDG of type CRSDG for the cluster's voting file and OCR, DATA of type DBDATAFILESDG for the database files, and FRA of type DBRECOVERY for the recovery area. The operator creates the PVs (manual Phase 7) and Grid creates VOTEDG during its install; the database groups follow before DBCA.
  • sshKeySecret, dbSecret: the Secrets from Phase 9, with the same OpenSSL settings used to encrypt the password.
  • image, imagePullPolicy: IfNotPresent: the slim image built on each worker in 8.1; IfNotPresent because it exists only locally.
  • resources, securityContext.sysctls: sizes from 11.1, and the kernel settings the manual lab put in its StatefulSets (10.4). kernel.shmmax must be at least the SGA and kernel.shmall at least SGA / 4096; 8 GiB and 2,097,152 pages cover the 3 GB SGA.

11.4 If DATA or FRA creation fails with ORA-15014 (what happened in this lab)

The first run of this lab, without CRS_ASM_DISCOVERY_STRING in the YAML, stopped right after the DB home install:

text
asmca -silent -createDiskGroup -diskGroupName FRA -redundancy EXTERNAL -disk '/dev/disk/by-id/ata-VBOX_HARDDISK_VB204551ec-…'
[FATAL] [DBT-30006] Exception while Processing Request.
   CAUSE: ORA-15018: diskgroup cannot be created
ORA-15031: disk specification '/dev/disk/by-id/ata-VBOX_HARDDISK_VB204551ec-…' matches no disks
ORA-15014: path '/dev/disk/by-id/ata-VBOX_HARDDISK_VB204551ec-…' is not in the discovery set

Cause: when Grid was configured, the setup script set ASM's discovery string from the first CRSDG disk only: /dev/disk/by-id/ata-VBOX_HARDDISK_VB67cb0647-80696c*. That pattern matches the vote disk and nothing else, so ASM couldn't see the DATA and FRA disks. The script marked itself failed and stopped. Grid, VOTEDG and both homes were fine.

Fix without starting over: widen the discovery string, then run the setup script again. It skips everything already done (unzips, Grid, DB home) and continues with the disk groups and DBCA.

a. Check the state (changes nothing):

kubectl -n rac exec racnode1-0 -c racnode1-0 -- su - grid -c "asmcmd dsget"

Check: state: failed; no main.py / runOracle line, or only short-lived main.py --checkracinst / --checkdbrole lines (the pod's health probes); dsget shows the single …VB<vote>…* pattern.

b. Widen the discovery string to all three disks. dsset writes it to both places ASM keeps it, the cluster profile (GPnP) and the ASM spfile in VOTEDG, so it's cluster-wide and survives restarts; nothing restarts.
